## What was changed, and what is still over budget

### Hot spots fixed (measured with `npm run perf:budgets`, mobile, simulated 4G, 4x CPU slowdown)
| Hot spot | Fix | Evidence |
| --- | --- | --- |
| The three Firebase SDK scripts were render-blocking in the `<head>` on eight pages (`clip`, `clips`, `listening`, `manga`, `placement`, `practice`, `whiteboard`, tools) | `defer` on every SDK script (they still run before the page's module scripts, which a unit test checks) | Lighthouse listed all three as render-blocking (up to 983 ms) on `clip.html`; after the change they are no longer listed. `clip.html` performance 86 to 89 |
| Every page opened a fresh connection to `www.gstatic.com` only when it reached the SDK script | `<link rel="preconnect" href="https://www.gstatic.com" crossorigin>` before the SDK scripts on every page that uses it | `portal.html` LCP 2.0 s to 1.4 s, `manga.html` 3.15 s to 3.0 s, `clip.html` 2.8 s to 2.7 s (same run conditions, one run each, so treat small changes as noise) |
| Each page discovered its 15 to 45 ES modules one import at a time (a request waterfall) | `<link rel="modulepreload">` for each page's own module graph, generated by `scripts/build-preload.mjs`; a test fails if a page is out of date | Not separately measurable above the run-to-run noise (about 0.5 s); kept because it removes the waterfall by construction |

The audit server now compresses text like GitHub Pages and Firebase Hosting do. Before this, uncompressed 171 kB of `lesson.js` made every number worse than a real visit; the earlier baseline in `docs/LIGHTHOUSE.md` was taken without compression.

### Not met, and why
- **LCP over 2.5 s on `clip`, `manga`, `lesson`, `homework`, `dashboard`** (2.5 to 3.7 s). These pages draw their content from JavaScript after the Firebase SDK has loaded and sign-in has been checked. In the audit (an anonymous visitor on a throttled phone) the last-painted element is the status message that appears after that round trip, so LCP is bounded by the SDK download plus the auth check, not by our own code. Removing it would need the modular SDK (v9+) with only the modules each page uses, which is a rewrite of every page's Firebase calls and was not done.
- **`lesson.html` and `dashboard.html` performance 88** (target 90). The trace of the signed-in lesson page (`node scripts/trace-page.mjs lesson "lesson.html?code=DEMOA001&lesson=sabina"`) shows one first-layout pass of about 600 ms at 4x CPU slowdown on 349 layout objects, and 6 tasks over 50 ms (longest about 670 ms). The cause was not found; candidates are first use of emoji and fallback fonts, and the 46 kB `lesson.css`. Not fixed.
- **INP** is not measured by the lab run; total blocking time (under 200 ms on every page) is the stand-in. Real INP needs field data.
- **Images and fonts:** the app has no raster images and uses system fonts, so WebP/AVIF conversion and font subsetting do not apply.
- **SEO score** is not asserted (every page is `noindex` on purpose).

### Where the JavaScript goes
`npm run check:budgets`: the largest page is `manga.html` at 98 kB gzipped of our own JavaScript, then `lesson.html` at 91 kB (plus 99 kB loaded only when needed). All pages are under the 150 kB budget; a test enforces it.
